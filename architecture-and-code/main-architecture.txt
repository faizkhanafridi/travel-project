2. Security rules to follow in every module

2.1 Authentication and account security
Authentication module is the foundation for the entire platform.
- Use Laravel Sanctum with an authentication approach appropriate to  deployment. For a first-party React SPA on the same top-level domain,
  prefer secure, cookie-based sessions rather than storing bearer tokens in browser storage.
- Use HTTPS everywhere in production.
- Store passwords using Laravel's secure password hashing.
- Require email verification before activating the account as specified in project.
- Hash verification and password-reset tokens at rest where practical; make them expire and invalidate them after use.
- Rate-limit login, registration, password reset, verification, resend verification, and social-login endpoints, store codes in hash form into db.
- Return generic login and reset responses where needed to reduce account enumeration.
- Invalidate sessions after logout, password changes, account compromise, or other sensitive security events.
- Add multi-factor authentication for SuperAdmin accounts. Consider it for Agents as well.
- Protect Google and Facebook login against OAuth state/redirect attacks; link social accounts only after verifying ownership.
- Never store passwords, session identifiers, API secrets, or private keys in frontend code or logs.

When the user clicks **Change Email**, show a modal with this content:

Update your account email address.

**New email address**

`new@example.com`

We'll send a 6-digit code to your current registered email address to authorize this change.

Buttons: **Cancel** | **Send code**

Link: **I can't access my current email**

### Standard email-change flow

1. User enters a new email address.
2. Send a 6-digit verification code to the current registered email address.
3. Verify the code securely.
4. Send a verification code to the new email address.
5. Verify the new email address.
6. Update the account email only after all required verification steps succeed.

The new email must remain unverified until the process is completed. Protect against expired codes,
 brute-force attempts, replay attacks, duplicate email addresses, and unauthorized email changes.

## 4. Alternative Flow — Can't Access Current Email

**Change email**

`guzyhi@mailinator.com`

**Current account password**

`Enter your current password`

After your password is verified, we'll send a verification code to the new email address.

Buttons: **Back** | Continue with verification

### Alternative email-change flow

1. User enters the new email address and current account password.
2. Verify the current password securely on the backend.
3. Send a 6-digit verification code to the new email address.
4. Verify the code.
5. Update the email only after successful verification.

Add rate limiting, code expiration, secure password verification, and protection against email enumeration.
 Never expose verification codes in API responses or logs.

For accounts that do not have a password, such as certain social-login accounts, handle the alternative verification 
flow securely without assuming a password exists.

 The Dynamic Commission Business Logic

The system tracks the payout splits at the database level by looking at how the booking started:
• Scenario A: Marketplace Services (Standard Booking & Agent Service Request Trip)
	• The Rule: The customer browsed the platform's public listings. There is no Connect fee for the agent, so the platform takes a 2% commission upon success.
	• The Math: Agent receives 98% of the total funds.
		• 2-Step Model: Phase 1 releases 70%. Phase 2 releases 28% (Total: 98%).
		• 1-Step Model: Final approval releases 98% instantly.
• Scenario B: Custom Trip Posts (Global Travel Board)
	• The Rule: The agent spent their paid Connects/Points to pitch for this client. To keep the platform attractive for high-quality bidders, 0% commission is charged on these wins.
	• The Math: Agent receives 100% of the total funds.
		• 2-Step Model: Phase 1 releases 70%. Phase 2 releases 30% (Total: 100%).
		• 1-Step Model: Final approval releases 100% instantly.


3. Trust Framework: Security Rules & The Verification Loop

To protect the customer's funds across both models, the platform runs a three-tiered automated safety pipeline:

• Simplified Independent Customer Verification: The moment an agent uploads any travel document file (PDF or Image), 
the customer's active order interface generates a clean dashboard action widget reading:
	• “The agent has submitted official travel documents. Please click [View Uploaded Document] to review the 
   credentials. Verify that your names and dates etc.. are correct. For local transport or hotels without websites, 
   please use the contact details provided inside the document to call/email the supplier directly and verify your
   reservation before approving the release of funds.”


• The 72-Hour Verification Window (For 2-Step Packages): Once the agent uploads Phase 1 documents, a timer gives
 the client exactly 72 hours to cross-check the references. If the customer clicks "Looks Good Continue" or lets the 72 hours
  lapse without filing a dispute, the system presumes legitimacy and unlocks the 70% escrow portion so the agent can 
   finalize payments with external suppliers.

• The 7-Day Inspection & Review Window (For Final Releases): For Phase 2 of packages, or the 100% release of 
Accommodations and Transport, the agent does not receive money until the customer explicitly clicks "Approve & Fund"
 or the 7-day safety timer runs out. If the customer spots an error, they click "Request Resubmit 'with reason'",
 which immediately  locks the funds in escrow and pauses all countdown clocks until the agent uploads fixed documents.
 
• Post-Release Fraud Clawback & Safety Net: If an agent maliciously cancels an accommodation or flight reservation 
after a milestone release, the platform deploys its Bonded Safety Pool (funded by transaction commissions) to 
refund the customer. Concurrently, the agent's account is permanently banned, active wallets are frozen, and the file 
is routed directly to collections.

• The "Refill Requirements" Ghosting: What happens if a customer pays, the agent asks them to refill 
broken requirements, and the customer disappears for weeks? the rule is If a customer fails to 
fix their requirements within 7 days of an agent's request, the booking is automatically cancelled, and the 
money is returned to the customer.

MODULE 11 — SYSTEM / ANALYTICS


Two types of activity tracking

A. Agent Activity & Performance
Agent dashboard — Fiverr-style


This shows agents their own business activity, progress, and performance.
- Services created, submitted, approved, rejected, or paused.
- Custom travel requests applied to and offers submitted.
- Bookings received, accepted, completed, and cancelled.
- Customer reviews and ratings.
- Response rate and response time.
- Connects earned, spent, and remaining, once the Connects system is integrated.
- Account warnings, restrictions, or suspension notices.
Visibility: Each agent can see their own activity and performance, not another agent's private information.


B. Platform / Admin Audit Log
Restricted internal administration


This records detailed, attributable actions across the platform for security, investigations, and accountability.
- Admin approved, rejected, or suspended an agent.
- Admin approved or rejected a service.
- Roles, permissions, and account status changed.
- Booking status, cancellation, and dispute decisions changed.
- Finance actions, refunds, commission adjustments, and payouts after Finance Module exists.
- Sensitive administrative settings changed.
- Failed authorization attempts and relevant security events.
Visibility: Only administrator/platfrom can access the audit logs.


Example: one action, two records
When an admin approves an agent:

Agent activity log
“Congratulations! Your agent application has been approved.”


Admin audit log
Records administrator approved which application, when it happened, and the relevant status change.


The two records serve different purposes. The agent receives a useful activity entry, while the platform retains the detailed administrative record.
